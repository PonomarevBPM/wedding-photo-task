# План реализации

## Текущее состояние

Реализованы основа Next.js, четыре задания, обязательное имя с сохранением на устройстве, камера и галерея, сжатие JPEG, превью, серверная загрузка на Диск, повтор отправки с проверкой сохранённого файла и переключатель приёма. Подготовлены инструкция и пример серверного окружения.

Сборка и проверка типов прошли; локальный сервер ранее отвечал HTTP 200. Автотесты исключены по решению пользователя. Локальный токен Диска настроен, доступ к метаданным подтверждён; JSON со списком заданий больше не создаётся. На VPS уже работают Nginx, HTTPS и автопродление через Snap. Пользователь удалил старую статику и применил конфигурацию `/etc/nginx/sites-available/default`, которая направляет запросы на `127.0.0.1:3100`. Docker Compose и GitHub Actions подготовлены: образ собирается на GitHub, передаётся по SSH и запускается на VPS с возвратом к предыдущему образу при неудачном запуске. Остаётся установить Docker Engine и Compose plugin, подготовить доступ для деплоя, настроить серверное окружение и secrets GitHub, запустить workflow и проверить фотографии на телефонах. Конкретные адреса сервера и данные владельца репозитория не записываются в файлы проекта.

Проверка VPS по SSH 15 октября 2026 года подтвердила: Nginx и Snap-таймер продления активны, HTTPS проходит проверку, приложение отвечает 502 до запуска контейнера. Docker, Compose, `rsync`, пользователь `deploy`, его `authorized_keys`, каталог приложения и серверный `.env.local` отсутствуют. Репозиторий Docker доступен, SSH по ключам разрешён. Инструкции обновлены под установку именно этих компонентов; сервер в ходе проверки не изменялся.

## Принятые решения

- Мобильное веб-приложение для одного свадебного мероприятия.
- Случайное задание с кнопкой «Другое задание».
- Повторы заданий между гостями и несколько фотографий на задание разрешены.
- Имя гостя обязательно, регистрация не требуется.
- Доступ по ссылке или QR-коду без пароля и общего кода.
- Фото сжимаются перед отправкой; оригиналы не сохраняются.
- Фотографии видит организатор на Яндекс Диске. Гостевой галереи в первой версии нет.
- Яндекс Диск — текущий выбор, его пригодность подтверждаем интеграционной проверкой.
- Размещение на VPS с Ubuntu через Docker Compose и GitHub Actions. Nginx на Ubuntu, домен `wedding-dinner.ru`, HTTPS и автопродление уже настроены. Жёсткий срок пока не задан.

## 1. Основа проекта и проверка загрузки

Подготовить Next.js с TypeScript, команды разработки, сборки и проверки типов. Добавить конфигурацию мероприятия и четыре согласованных задания со стабильными идентификаторами:

| Идентификатор | Задание |
| --- | --- |
| `groom-smile` | Сфотографируй, как жених улыбается. |
| `groom-friends` | Поймай момент, когда жених обнимается с друзьями. |
| `bride-friends` | Сфотографируй невесту с подругами. |
| `couple-selfie` | Сделай совместное фото с молодожёнами. |

Пример переменных окружения содержит только названия и заглушки: токен Диска, корневую папку и настройку приёма фото.

Сначала реализовать минимальный серверный маршрут отправки и проверить путь от маленького JPEG до приватной папки Диска. Проверить локально, затем в развёртывании на VPS: так ограничения интеграции обнаружатся до завершения интерфейса.

Контракт отправки: `POST /api/photos`, `multipart/form-data`, поля `photo`, `guestName`, `taskId`, `uploadId`. Идентификатор мероприятия сервер берёт из конфигурации. Успешный ответ содержит идентификатор отправки; ошибки имеют код и понятное сообщение, без токенов и внутренних ссылок загрузки.

Результат: тестовое фото действительно появляется на Диске. Для реальной проверки понадобится OAuth-токен организатора в серверном окружении; его отсутствие не мешает готовить интерфейс, но проверка интеграции остаётся незавершённой.

## 2. Имя гостя и выдача заданий

Сделать экран приветствия с обязательным именем. Удалять пробелы по краям, проверять непустое значение и разумную длину как в браузере, так и на сервере. Запоминать имя на устройстве, предусмотреть редактирование; при недоступности локального хранилища приложение продолжает работать.

Показывать случайное задание. Если заданий несколько, кнопка «Другое задание» исключает текущее из следующего выбора. Если задание одно, кнопку скрыть. Глобальное распределение и резервирование заданий не нужны. После загрузки разрешить ещё одно фото по текущему заданию или переход к другому.

Результат: гость может указать имя, получить и сменить задание; разные гости могут выполнять одно задание.

## 3. Камера, подготовка фото и превью

Добавить кнопки съёмки основной камерой и выбора из галереи. Отмена камеры возвращает к заданию. Подготовку фото выполнять в браузере: учитывать ориентацию, уменьшать большие изображения и сжимать в JPEG до 3 МБ.

Начальные параметры для подбора: до 2560 пикселей по длинной стороне, качество JPEG около 0,85; при превышении размера снижать качество или разрешение. Проверить итог на портретах и групповых фотографиях. Неподдерживаемые форматы обрабатывать явным сообщением; поддержку HEIC определить по проверке реальных устройств и при необходимости добавить конвертацию.

Превью показывает именно подготовленный файл и задание. «Переснять» заменяет фото. Пока открыто превью, выбранное задание остаётся закреплённым за фотографией.

Результат: гость видит будущую отправку и может переснять; отмена и ошибки обработки не ломают сценарий.

## 4. Надёжная отправка и организация архива

Соединить интерфейс с серверным маршрутом. Во время отправки блокировать повторное нажатие, смену задания и замену фотографии. При ошибке сохранять подготовленный файл в текущей странице и предлагать повтор; после подтверждения очищать его.

На сервере проверять имя, существование задания, формат идентификатора отправки, размер файла и фактический формат JPEG. Путь строить только из проверенных данных; пользователь не передаёт путь Диска. OAuth-токен используется исключительно сервером.

Сохранять фото по заданию с именем файла `<имя-гостя>__<upload-id>.jpg`. Повтор отправки использует тот же идентификатор и путь, с запретом перезаписи. Если файл уже существует, проверить соответствие сохранённому содержимому перед подтверждением успеха. Для нового снимка создавать новый идентификатор. На Диск загружаются только фотографии, без JSON со списком заданий.

Добавить понятные сообщения для потери сети, тайм-аута, недоступности Диска и остановленного приёма. Ошибка конфигурации токена видна организатору в серверных журналах, а гостю — как временная невозможность отправить фото.

Результат: подтверждённая отправка появляется на Диске с автором и заданием; повтор запроса после сбоя не создаёт дубликат.

## 5. Доступ и проверка на телефонах

Гостевой доступ открыт по ссылке или QR-коду, без пароля и общего кода. Серверный переключатель приёма фотографий реализован. Ограничение частоты отправок в текущем Nginx не настроено; это отдельная задача перед массовым запуском с учётом общего Wi-Fi гостей.

Проверить полный сценарий вручную на iPhone/Safari и Android/Chrome: ввод имени, камера, галерея, портретные и горизонтальные фото, отмена съёмки, большие файлы, неподдерживаемый формат, повторное нажатие и повтор после потери сети. Проверить сборку и типы. По решению пользователя автотесты не добавляем и не запускаем.

После оценки числа гостей проверить несколько одновременных загрузок и время ожидания при медленном интернете. Проверить приватность папки, отсутствие токена в клиентском коде и соответствие фотографии её заданию и автору.

Результат: основные сценарии проверены на реальных телефонах; загрузка подтверждена в размещённом приложении.

## 6. Оформление и запуск

Проверить тексты четырёх согласованных заданий, добавить имена молодожёнов и оформление. Подготовить инструкции организатору: где фотографии, как сменить задания, настроить токен и остановить приём.

Домен, Nginx, сертификат и автопродление уже настроены. Подготовить SSH-доступ для Actions и серверное окружение, затем запустить контейнер через workflow. Проверить приложение по существующему HTTPS-адресу и сделать QR-код. Перед мероприятием проверить свободное место на Диске, доступность сайта из российских сетей и с площадки, затем контрольную отправку фотографии.

Результат: постоянная ссылка и QR-код открывают готовый сценарий, организатор знает, где смотреть фотографии.
